# 修复记录：已下载图片无法读取（JPEG 尾部数据 / XOR 推导）

整理日期：2026-10-05。排查版本：agent-wechat `v0.15.1`。
状态：已完成只读定位，尚未修改代码或部署修复。

## 现象与已确认原因

聊天中的普通图片长期显示“正在从微信读取”。图片文件实际上已下载到容器，
AES 解密成功，但账号未保存 `_image_xor`；AW 从 JPEG 最后两个字节推导 XOR
参数时失败，最终没有返回可用图片数据。

关键差异：样本的 JPEG 结束标记 `FF D9` 后还有尾部数据，文件最后两个字节
并非 JPEG 结束标记。尾部数据的来源与含义尚未确认。

## 排查证据

- 同一图片的 `quality=thumbnail` 请求等待约 20 秒，返回 `type=image`，
  但没有 `data` 或 `url`；`quality=best` 等待约 20 秒后返回 `type=pending`；
  `quality=standard` 也未返回图片数据。
- 媒体日志已找到本地 `.dat` 文件；文件头符合 `DAT_MAGIC`，保存的 AES
  密钥可以成功解密图片头，账号没有保存 `_image_xor`。
- 两份缩略图和一份原图的 JPEG 文件尾 XOR 推导均失败。
- 在内存中从尾部附近的结束标记生成 XOR 候选，并使用 FFmpeg 严格解码，
  三份 JPEG 各有一个可完整解码的候选。两份缩略图在结束标记后各有 24 字节，
  原图有 191 字节。
- standard 缓存的解密头为 WXGF；本轮未验证其完整转换结果，不能将 JPEG
  校验结果直接推广到 WXGF。

排查未手动改写密钥或缓存文件，未重启容器或发送消息；媒体 GET 沿用上游
自动下载行为。本文不包含真实图片、消息内容、账号身份、资源路径或密钥值。

## 需要修改的位置

| 文件 / 函数 | 当前问题 |
| --- | --- |
| `packages/agent-server-rust/src/tools/wechat_media.rs`：`derive_xor_byte()` | JPEG 分支假设文件最后两字节是 `FF D9`，无法处理结束标记后的数据。 |
| 同文件：`resolve_xor_byte()` | 未保存 XOR 参数时依赖上述推导；同目录缩略图也带尾部数据，回退仍然失败。 |
| 同文件：`decrypt_and_return()` | XOR 推导失败返回空的 `type=image`；即使修复推导，后续严格文件尾校验仍会阻止返回。 |
| `docker/tools/media-convert.py`：`validate_image()` | JPEG 必须满足 `data.endswith(b'\xff\xd9')`，会拒绝本轮已确认可完整解码的样本。 |

## 修复建议

1. 保留已保存 XOR 参数和现有推导的优先路径；推导失败时增加有界的 JPEG
   候选恢复。限制扫描范围、候选数量和解码耗时，不能只凭出现 `FF D9`
   就接受候选，需验证 JPEG 结构并完整解码；多候选无法确定时保留失败状态。
2. 同时调整 JPEG 完整性校验，支持真实结束标记后的尾部数据。可在确认
   JPEG 结构和结束位置后规范化输出，再执行现有严格 FFmpeg 校验。不要
   简单截取最后一个 `FF D9`，也不要关闭截断或损坏检查。仅在内存处理，
   不改写微信缓存文件。
3. 统一“没有可用图片字节”的返回语义，优先返回明确的 `pending`，避免
   空 `type=image` 被误认为成功。增加不含身份、密钥或资源路径的失败阶段
   日志，例如 XOR 推导失败、解密失败、格式校验失败。
4. 保持 `thumbnail` / `standard` / `full` / `best` 的质量语义、原生下载
   去重和等待上限；`full` 不应以缩略图代替。媒体 GET 不应切换聊天。

## 验收条件

- 用自造 JPEG 和 `.dat` fixture 覆盖：无尾部数据、结束标记后附加
  24 / 191 字节、未保存 XOR 参数、同目录缩略图回退。
- 错误密钥、错误 XOR、截断图片、伪结束标记和多候选无法确定的情况，
  仍不得返回成功图片；校验 PNG / GIF / WebP / WXGF 路径没有回归。
- Rust 媒体测试与 `media-convert` 校验通过。在隔离测试容器中确认媒体
  接口返回非空 `data`、正确格式及适用的 `quality`，并在客户端实际显示。
- 用户可见行为修复完成后，按仓库 `AGENTS.md` 添加对应 changeset。

## 下游界面问题（另行修复）

下游 Web 客户端收到 `pending` 后最多查询 8 次，随后停止查询，但仍保留
“正在从微信读取”提示，且没有超时重试入口。每次上游请求可能等待约 20 秒，
不能把 8 次查询简单理解为约 16 秒。

界面需要区分正在读取、查询已结束和失败，并提供可重新启动查询的重试操作。
这属于独立修复；仅修复界面状态无法恢复 AW 的图片解密。
